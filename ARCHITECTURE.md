# health-monitor-service — Architecture & File Guide

## 1. What kind of project this is

This **is** a proper npm package, not a standalone app:

- `package.json` name: `@monitor/health-service`, `"files": ["dist", "README.md"]`, `"publishConfig": {"access": "public"}` — it's built (`tsc`) into `dist/` and meant to be `npm install`-ed by other apps, or consumed by copying the built output.
- It also ships two **usage modes**:
  1. **Library mode** — import `startHealthMonitor()` (or the lower-level pieces) directly into another app's process (see `examples/octopulse-integration.ts`).
  2. **Standalone service mode** — `examples/basic-server.ts` runs it as its own small HTTP server, polled by an external cron (e.g. cron-job.org) or a platform scheduler.

**Language: TypeScript** (compiled to CommonJS JS via `tsc`, target `ES2022`, `strict: true`). Runs on Node.js ≥ 18. No runtime dependencies — only `dotenv`/`typescript`/`tsx` as dev tooling.

## 2. The core idea

A **registry** of named async health checks (CPU, memory, disk, an HTTP ping, or your own custom ones) gets run on a schedule. Results are classified `ok` / `warning` / `critical`, turned into a provider-agnostic `AlertPayload`, and fanned out to one or more chat webhooks (Teams, Slack, Discord, Power Automate). Optional AI (Claude) root-cause analysis can be attached when something's wrong. Per-check **cooldown**, **history/escalation**, and **snooze** state prevent alert spam and add trend/streak context.

## 3. Directory map

```
src/
  types.ts            shared types (CheckResult, HealthCheck, MonitorConfig)
  config.ts           build MonitorConfig from env vars + cron auth check
  registry.ts          HealthCheckRegistry — named collection of checks
  runner.ts            orchestration: run all checks -> report/alert
  notify.ts            builds AlertPayload from results, sends via channels
  cooldown.ts          AlertCooldown — rate-limits repeat alerts per check
  history.ts           HistoryStore — rolling per-check history (streak/trend)
  snooze.ts            SnoozeStore — temporary suppression per check or "all"
  analysis.ts          optional AI (Claude) root-cause analysis hook
  schedule-time.ts      timezone math for "next local HH:MM" + display formatting
  server.ts            minimal http.Server exposing the HTTP endpoints
  quickstart.ts        startHealthMonitor() — one-call, timer-driven integration
  index.ts             public export surface (the package's "API")
  checks/
    cpu.ts, memory.ts, disk.ts, http-ping.ts   built-in HealthCheck factories
    index.ts             re-exports
  channels/
    types.ts             NotificationChannel / AlertPayload contracts
    teams.ts, slack.ts, discord.ts, power-automate.ts   per-provider senders
    index.ts             re-exports
examples/
  basic-server.ts           standalone-service usage (the deployable example)
  octopulse-integration.ts  library usage inside a host app
dist/                built output (JS + .d.ts), generated by `npm run build`
```

## 4. File-by-file logic

### `src/types.ts`
Defines the shared vocabulary: `CheckStatus` (`ok`/`warning`/`critical`), `CheckResult` (what one check returns — name, status, message, optional numeric `value`/`latencyMs`/`details`), `HealthCheck` (`() => Promise<CheckResult>`), `OverallStatus` (`healthy`/`degraded`/`unhealthy`), and `MonitorConfig` (service name, webhook URLs, timezone, `isProduction` flag, `channels[]`, optional `analysis` provider). `name` on `CheckResult` is the stable key used everywhere else (cooldown, history, snooze) — it must stay constant run-to-run for the same logical check.

### `src/registry.ts`
`HealthCheckRegistry` — a thin `Map<string, HealthCheck>` wrapper with `register()/unregister()/list()`. You build one of these per app, registering whatever checks matter (CPU/memory/disk plus your own DB/API pings).

### `src/checks/*.ts`
Each file is a **factory** that returns a `HealthCheck` closure, configurable via an options object with warn/critical thresholds:
- `cpu.ts` — compares 1-minute load average to CPU core count (ratio-based thresholds).
- `memory.ts` — used-memory percentage via `os.totalmem()/freemem()`.
- `disk.ts` — shells out to POSIX `df -Pk <path>`; returns a `warning` (not a throw) on Windows since `df` doesn't exist there.
- `http-ping.ts` — generic "is this URL reachable" check with a timeout (`AbortController`) and latency-based warning threshold; non-2xx or timeout = `critical`.

All are dependency-free (built on Node's `os`/`child_process`/`fetch`), so the package has zero runtime npm dependencies.

### `src/runner.ts`
The orchestration core:
- `runAllChecks()` — runs every registered check via `Promise.allSettled` so one throwing check can't crash the others; a thrown check becomes a synthetic `critical` result instead of a silent gap.
- `tryAnalyze()` — calls `config.analysis.analyze()` only if there's at least one non-`ok` result; swallows/logs any error so a broken AI provider never blocks an alert.
- `runDailyReport()` — runs all checks once, records to `HistoryStore`, sends **one** summary card covering every check, and (if anything is non-ok) **one** additional combined incident message. No cooldown gating — it's once a day, duplicates aren't a concern. No-ops if `config.isProduction` is false.
- `runCriticalCheck()` — runs all checks, filters to non-ok, splits off anything currently **snoozed**, then gates the remainder through `AlertCooldown` (separate cooldown keys for `critical` vs `warning:<name>` so a check can escalate independently). Everything that passes the gate goes into **one** combined incident message (not one message per failing check) — reducing alert-fatigue for simultaneous failures. Meant to be called every 15–30 minutes by an external trigger.

### `src/notify.ts`
Turns `CheckResult[]` into the transport-agnostic `AlertPayload` and sends it:
- `computeOverallStatus()` — any `critical` → `unhealthy`; else any `warning` → `degraded`; else `healthy`.
- `buildDailyReport()` — one fact per check plus overall status/time; summary line depends on overall status.
- `buildIncidentReport()` — one fact per non-ok check, annotated with an escalation streak label (e.g. "(3x in a row)") sourced from `HistoryStore.consecutiveNonOk()`.
- `sendNotification()` — resolves the channel list (`config.channels` if set, else legacy `teamsWebhookUrl`/`powerAutomateWebhookUrl` fields for back-compat) and calls `channel.send()` on all of them in parallel via `Promise.all`, catching per-channel errors so one dead webhook doesn't stop the others. Returns `true` if **any** channel accepted the message.

### `src/cooldown.ts`
`AlertCooldown` — in-memory `Map<key, {lastAlertTime, count}>`. `shouldSend(key)` allows an alert if the cooldown window (`30 min` default) has elapsed, or if within the window but under `maxPerPeriod` (3 default) prior alerts. Purpose: stop a flapping check from spamming the channel every cycle. State is per-process — resets on redeploy/cold start, which is an accepted tradeoff.

### `src/history.ts`
`HistoryStore` — in-memory rolling window (last 20 entries by default) per check name. Powers two things a single point-in-time `CheckResult` can't: `consecutiveNonOk(name)` (streak length, counted back from the latest entry until the first `ok`) and `trend(name)` (`rising`/`falling`/`flat`/`unknown`, comparing the oldest vs newest numeric `value` in the retained window, with a ±5 deadband).

### `src/snooze.ts`
`SnoozeStore` — `Map<key, expiryTimestamp>`. `snooze(key, durationMs)` suppresses alerting for a specific check name, or everything via the special key `'all'`. Checks still run and are still recorded to history while snoozed — they're just excluded from the alert-worthy set. Used for planned maintenance windows without disabling the whole integration.

### `src/analysis.ts`
Optional hook interface `AnalysisProvider.analyze(results, context) -> {summary, suggestions}`, invoked by `runner.ts` only when something is non-ok. `anthropicAnalysisProvider()` is the bundled implementation: builds a short SRE-style prompt from the failing checks, calls the Claude Messages API (`https://api.anthropic.com/v1/messages`) directly via `fetch` (no SDK dependency), and returns the response text. Never called unless `MonitorConfig.analysis` is explicitly set (i.e., an API key was provided) — the package makes no LLM-vendor assumption; you can write your own provider for another vendor by implementing the same interface.

### `src/schedule-time.ts`
Timezone utilities with no external date library:
- `timezoneOffsetMs()` — uses `Intl.DateTimeFormat` to compute how far an IANA timezone's wall clock is from UTC at a given instant (recomputed per call so DST transitions self-correct).
- `msUntilNextLocalTime(timezone, hour, minute)` — how long until the next occurrence of a local `HH:MM`, used to schedule the daily report at a fixed local time rather than "24h after process boot."
- `formatInTimezone()` — human-readable timestamp for outgoing messages.

### `src/config.ts`
- `loadConfigFromEnv()` — builds a `MonitorConfig` from environment variables (`SERVICE_NAME`, `*_WEBHOOK_URL` vars — any combination becomes a channel, so one run can alert Teams **and** Slack **and** Discord simultaneously — `TIMEZONE`, `NODE_ENV`, `ANTHROPIC_API_KEY`/`ANALYSIS_MODEL`). Intended for the standalone-server usage; library consumers are expected to build `MonitorConfig` themselves from their own app's env handling.
- `isAuthorizedCronRequest()` — validates `Authorization: Bearer <cronSecret>` using SHA-256 hash + `timingSafeEqual` (constant-time comparison, avoids leaking timing info about the secret, and avoids throwing on length mismatch). **Fails closed**: if no `cronSecret` is configured, every request is rejected.

### `src/server.ts`
`createServer(registry, config)` — a dependency-free `http.Server` (no Express) exposing:
- `GET /` or `/healthz` — unauthenticated liveness probe; returns `lastSuccessfulRun` as a cheap dead-man's-switch (if it goes stale, the external scheduler has stopped calling in).
- `GET /health-report` — runs `runDailyReport()` (auth required).
- `GET /critical-check` — runs `runCriticalCheck()` (auth required).
- `POST /snooze` — body `{check?, minutes?}`, calls `SnoozeStore.snooze()` (auth required).
All routes except the liveness probe check `isAuthorizedCronRequest()`. `AlertCooldown`/`HistoryStore`/`SnoozeStore` are instantiated once per server and closed over by the request handler, so state persists across requests for the life of the process.

### `src/quickstart.ts`
`startHealthMonitor(opts)` — the "one call and you're done" integration path for apps that already have a long-lived Node process (no separate deployed service, no external cron needed). It:
1. Builds `NotificationChannel[]` from flat webhook-URL options.
2. Builds `MonitorConfig`, registers built-in cpu/memory/disk checks (optional, `includeDefaultChecks`) plus any custom `opts.checks`.
3. Fires one critical check immediately (so a failure present at startup is caught right away), then re-runs it on a `setInterval` (`criticalIntervalMinutes`, default 15).
4. Schedules the daily report via `setTimeout` to the next local `hour:minute` (using `msUntilNextLocalTime`), then **re-arms itself for the following day after each run** — deliberately not a flat 24h `setInterval` from whenever the process happened to boot, so the time-of-day stays fixed even across restarts.
5. Returns a handle with `.stop()` to clear both timers on app shutdown.
Use this instead of `createServer()` only when your process stays alive continuously; for serverless, use the server/cron-endpoint pattern instead.

### `src/index.ts`
The package's public API surface — re-exports types, `loadConfigFromEnv`/`isAuthorizedCronRequest`, `HealthCheckRegistry`, `AlertCooldown`, `HistoryStore`, `SnoozeStore`, the runner functions, `notify.ts` builders, built-in checks, `createServer`, everything from `channels/`, everything from `analysis.ts`, and `startHealthMonitor`. This is what `import { ... } from '@monitor/health-service'` resolves to.

### `src/channels/types.ts`
The channel contract: `AlertPayload` (provider-agnostic message shape — title, summary, `Fact[]`, `Action[]`, optional `AnalysisBlock`) and `NotificationChannel` (`{name, send(payload) -> Promise<boolean>}`). Anyone can implement a new channel by satisfying this interface — no core code changes needed.

### `src/channels/{teams,slack,discord,power-automate}.ts`
Each exports a factory `xChannel(webhookUrl) -> NotificationChannel` that POSTs the payload translated into that provider's native wire format:
- **teams.ts** — Adaptive Card (`TextBlock`/`FactSet`/`ActionSet`), color mapped to Teams' `Good`/`Warning`/`Attention`.
- **slack.ts** — Block Kit; chunks `facts` into groups of 10 because Slack section blocks cap fields at 10.
- **discord.ts** — Embed object; caps fields at 25 (Discord's embed limit), truncates AI analysis text to 1024 chars (Discord field value limit); expects `204 No Content` on success.
- **power-automate.ts** — sends the raw `AlertPayload` JSON as-is, since the receiving Power Automate flow does its own "Parse JSON" + branching — this package makes no formatting assumption for that one.
All four fail soft: a non-OK response or thrown error is caught, logged, and returns `false` rather than throwing — so one broken webhook doesn't take down the others (`sendNotification` sends to all channels in parallel and only needs one success).

### `examples/basic-server.ts`
The **standalone-service** example/entry point. Loads config from env, registers the built-in checks plus a self-ping against its own `/healthz`, then branches on CLI args: `--report` / `--check` run a single pass and exit (used by `npm run report:once` / `check:once` for local testing), otherwise it starts the HTTP server (`npm run dev`/`start`).

### `examples/octopulse-integration.ts`
The **library-usage** example: shows importing the package into an existing host app (referred to as "Octopulse"), building `MonitorConfig` from that host app's own env conventions, adding a project-specific check (`databaseCheck`, a Prisma-shaped placeholder) that intentionally stays out of the package itself since it's app-specific, and wiring `dailyReport`/`criticalCheck` for the host app to call from its own cron routes (e.g. Next.js route handlers). Excluded from the `tsc` build (see `tsconfig.json` exclude list) since it's documentation-by-example, not compiled output.

## 5. Request/data flow summary

```
HealthCheckRegistry (named checks)
        │
        ▼
runner.ts: runAllChecks()  ──► HistoryStore.record()  (trend/streak tracking)
        │
        ▼
   filter non-ok  ──► SnoozeStore.isActive()  (drop snoozed)
        │
        ▼
   AlertCooldown.shouldSend()  (drop rate-limited)
        │
        ▼
analysis.ts (optional, only if non-ok exists)
        │
        ▼
notify.ts: buildDailyReport()/buildIncidentReport()  ──►  AlertPayload
        │
        ▼
notify.ts: sendNotification()  ──►  fan out to every configured NotificationChannel
                                     (teams / slack / discord / power-automate)
```

Triggering side (pick one):
- **External cron** hits `server.ts`'s `/health-report` or `/critical-check` (bearer-token authed).
- **In-process timers** via `quickstart.ts`'s `startHealthMonitor()`.
- **Manual/host-app cron route** calling `runDailyReport()`/`runCriticalCheck()` directly (library mode, see `octopulse-integration.ts`).
